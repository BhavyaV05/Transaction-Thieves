# E13 on the LLM planner: batched questions (T3 rows)

Owner: T3 (Akshat). Spec: plan.md section 8 row E13 (H8: "two questions at once, then one more keeps 80 percent of the benefit in 60 percent of the time"), tracks.md async-mode notes. T2 owns E13 and the non-LLM rows; this is the LLM planner's arm. Branch `t3/planner-batched`.

## What was built

`LLMPlanner(batch_schedule=(2, 1))`, CLI `run_llm_agent.py --system planner --batch-schedule 2,1` (recorded in `summary.json` as `batch_schedule`). Off by default; the sequential loop, prompt and schema are unchanged when it is off.

- **Definition (matches T2's `waves=(2, 1)`, `ftm/planners/simple.py`).** Planner step i proposes up to `schedule[i]` questions; they go out as one wave through `Investigation.ask_wave` (the harness `ask_banks`; the wave costs its slowest answer); stop rules are checked before each wave; no two questions of one family in a wave; the wave's eps must fit the eps left together; the investigation ends when the schedule is used up (no extra stop call). A step that fails (bad JSON, bad DSL for every question, everything refused) is retried and does not use up a schedule slot, but costs a call as before. Caps (20 calls, eps 2.0, 6,000 prompt tokens, 5 sim days) and the 3-failures-in-a-row rule are unchanged.
- **Schema.** A step with k > 1 uses `planner_wave_step`: `action` is `ask | stop`, `questions` is an array of 0 to k items, each item `{action: select|compose, question_id, program, bank, eps, rule_id}` with the same enums as the single-question schema (menu ids, partner banks, non-zero eps levels, the program pattern). Steps with k = 1 (and every step when the option is off) use the original schema. Both are guided-decoded. The prompt's Output section tells the model it is a wave (same family twice is dropped, eps adds up, answers are not seen before all come back).
- **Differences from T2's planners.** (a) T2's `one_per_family` also applies across waves (a family asked in wave 1 is not offered in wave 2, via `PlanSession.affordable`); here it applies within a wave only, because the sequential LLM loop has no such rule and the model sees the earlier answers. (b) T2 picks the second question with the planner's own rule; the LLM proposes both blind to each other's answer. (c) T2's eps rule drops what does not fit; here a non-fitting question is dropped and logged (`wave_over_eps`, `select: not enough eps`), the others still go. Otherwise the same.
- Tests: `tests/test_planner_batched.py` (mock LLM + mock harness clock): a 2-question wave advances the clock by the max, then one single, then the loop ends with no extra call; schema allows lists only at batched steps; sequential path unchanged.

## Reading it

The batched arm did not batch in practice. The per-alert eps budget is 2.0 and the accepted menu questions are back-tested at eps 1 (5 rows) and 2 (18 rows) only, so the first question uses the whole budget: every one of the 20 waves went out with exactly one question (16 second questions were dropped as "not enough eps", 4 as "does not fit with the first"), and the (2, 1) schedule never reached its second step. The two arms asked 21 questions each. So there is no wave clock effect to measure here: the sim-day and Brier differences come from the model picking different first questions under the wave prompt (`n_new_counterparties` 7 times instead of 2; Brier moves with it), not from batching. Wall time is slightly higher in the batched arm because the wave output is longer. The wave mechanics (clock = max of the answers, one `ask_banks` call, partial refusals) are covered by the unit tests, not by this run.

Consequence for E13 on the LLM planner: with eps 2.0 per alert and no accepted question below eps 1, a (2, 1) schedule is only usable if both questions are back-tested at eps 1 or less (5 accepted rows at eps 1 now; none at 0.25 or 0.5). A real LLM E13 row needs either more accepted low-eps questions in the back-test table (T2/T4) or a larger per-alert budget for both arms; the batched arm cannot be compared on time until waves actually contain two questions. Not run: the supplementary arm with a larger budget (the toolbox takes the smaller of `Limits.eps_per_alert` and its accountant's, and there is no CLI for it yet).
