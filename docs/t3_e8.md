## Finding: Gemma 4 overflows the prompt cap on a fifth of alerts (fixed)

The first E8 pass (26 Oct 08:13-08:54) gave `amount` Brier 0.1985 = p0 exactly: **every one of its 160 alerts ended with `PromptTooLong`** on step 1 (server counted 6,032-6,308 tokens > cap 6,000), so the planner never answered and every verdict fell back to p0. Cause: the planner's trim loop estimates tokens with a character rule fitted on the Qwen tokenizers (`CHARS_PER_TOKEN` 3.2 plus `EVIDENCE_EXTRA_TOKENS_PER_CHAR` 0.30 for evidence rows); Gemma 4's tokenizer counts about 5% more, so prompts trimmed to "6,000" arrive at 6,000-6,300. The server count is checked after the call, and the planner then ended the alert. Full 40-row trails (`amount`, most `long_prompt`) always hit it; the stub's 1-hop trail often has fewer rows, so it hit less often.

Alerts that ended at p0 because of this, in runs so far:

| Run | Alerts with PromptTooLong | Token range |
|---|---|---|
| E18 stage 1, Gemma 4 12B (160 eval) | 35 (22%) | 6,002-6,182 |
| E18 stage 2, Gemma 4 12B (460) | **120 (26%)** | 6,001-6,232 |
| E18 stage 2, Qwen3.8-27B Q3 | 3 | 6,004-6,030 |
| E18 stage 2, Qwen3-14B | 0 | - |
| E18 sensitivity, gpt-oss-20b 1,024 out (460) | 0 | - |
| Teacher runs, Gemma 4 12B (1,983 train) | 393 (20%) | 6,001-6,308 |
| E8 first pass: `amount` / `amount_1hop` / `long_prompt` | 160 / 35 / 126 | 6,001-6,308 |

**Effect on E18 (sensitivity, not a re-decision).** On the 460 stage-2 alerts, dropping the 123 where any of the three finalists overflowed (340 left, p0 0.1677): Gemma 4 12B 0.1727, Qwen3.8-27B 0.1812, Qwen3-14B 0.1853; Gemma - 27B -0.0085 [-0.0213, 0.0062] (on all 460: -0.0104 [-0.0218, 0.0021]). **Gemma stays first**, so the pick does not change; the p0 fallback had widened its lead a little (on the 120 overflow alerts p0 scores 0.1780 and the other two models 0.1936 / 0.1993). Against the labelled gpt-oss-20b 1,024-token arm: tied on all 460 (0.1741 each), on the 340 clean alerts gpt-oss 0.1691 vs Gemma 0.1727, diff -0.0035 [-0.0142, 0.0069] (not significant). T4 to decide whether E18 stage 2 is re-run for Gemma with the fix (about 45 min) before the result is final.

**Fix** (`ftm/planners/llm.py`, `ftm/planners/llm_prompt.py`, `ftm/llm/budget.py`). `PromptTooLong` carries the server's count. When the server counts a prompt over the cap, the planner sets a per-alert `token_scale = server count / estimate x 1.02`, rebuilds the step with the trim loop using the scaled estimate (oldest evidence rows go first, as before), and resends, at most twice per alert. The over-long call stays counted in the alert's LLM calls, tokens and GPU seconds (the cap still binds the same way for every system). The scale starts at 1.0 for every alert, so results do not depend on alert order. Qwen runs are unaffected (no overflow, scale stays 1.0). Test: `tests/test_planner_quality.py::test_server_counted_overflow_refits_the_prompt_instead_of_dropping_the_alert`.

The Group D ports and the Group C ports do not trim their prompts at all; they will show any overflow as `PromptTooLong` in their traces. They are checked on their first Gemma val runs.
