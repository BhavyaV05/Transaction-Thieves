## Parity (plan §6.11)

Same for every candidate: alerts (a seeded shuffle, so the 160 stage-1 alerts are a prefix of the 460), seed 0, `Limits` (`max_tokens` 6,000 is read from `configs/llm/default.yaml` and must equal `parity.max_prompt_tokens`), prompt text (each model's own chat template), temperature 0, top-40 evidence. Thinking off (`enable_thinking: false`); gpt-oss at `reasoning_effort: low`. Before deciding, `check_parity` compares the alert hash, ids, seed, data, val part and limits of every run dir and raises `ParityError` on any difference.

## Commands

The 16 GB GPU holds one candidate at a time: serve a candidate, run it, switch. `--only a,b` runs just those candidates (the decision still waits for the whole stage). The driver skips a candidate whose endpoint does not list its `served_model`, and skips one whose run dir is complete (`summary.json` with the right alert count and settings). An incomplete run dir is deleted and rerun. The decision is applied once every candidate of the stage is complete.

```bash
# plan and GPU-hour estimate (8-20 s per alert; thinking arm 5-9 h per 500 alerts, scaled to 460); touches no data, no endpoint
python scripts/run_e18.py stage1 --val-part eval --dry-run --sets core,if_time

# stage 1: 160 alerts per candidate (FTM_LLM_ENDPOINT / FTM_LLM_API_KEY as usual; --machine t3-5070ti for timing)
python scripts/serve_llm.py --profile qwen3-8b              # one candidate at a time
python scripts/run_e18.py stage1 --val-part eval --only qwen3-8b --machine t3-5070ti --clusters clusters.json
...                                                          # next candidate; the last call writes decision.json

# stage 2: the top 3 from stage 1 (outputs/e18/stage1/decision.json), 460 alerts, stage-1 alerts first
python scripts/run_e18.py stage2 --val-part all --only gpt-oss-20b --machine t3-5070ti    # --models a,b,c overrides the stage-1 top 3
python scripts/run_e18.py stage2 --val-part all --only <last model> --machine t3-5070ti --clusters clusters.json --margin-json margin.json

# thinking-on arm for the stage-2 winner: 1,024 output tokens per step, same 460 alerts
python scripts/run_e18.py thinking --val-part all --machine t3-5070ti --clusters clusters.json --margin-json margin.json

# tabulate and decide from existing run dirs, no model calls
python scripts/run_e18.py stage2 --val-part all --summarize-only --clusters clusters.json --margin 0.01

# whole driver offline against the mock server (python -m ftm.llm.mock --port 8001 --model qwen3-8b)
python scripts/run_e18.py stage1 --alerts synthetic --n 6 --only qwen3-8b --endpoint http://127.0.0.1:8001/v1 --out outputs/e18_smoke
```

Notes: `--val-part` is required with val alerts and has no default (see Questions). `--toolbox` defaults to `harness` (needs T2's harness v0); `dev` is allowed with synthetic alerts only. `prereg/e18_decision.yaml` must have `status: committed` before a real run (`--allow-draft-prereg` overrides; its status and hash go in every `summary.json`). `margin.json` is `{"brier_random": x, "brier_best_simple": y}` measured on the same 460 alerts; the margin is `0.5 * |difference|` (`ftm.eval.stats.equivalence_margin`).

## Per-candidate procedure

The week-0 check "does each candidate load at the context cap" is not done up front. It is part of the sweep, one candidate at a time, so `/` never holds more than one large model (about 100 GB free):

1. Download the candidate once, at its pinned revision, into `FTM_HF_HOME` (for repos that ship extra weight copies, such as `original/` or `metal/`, exclude them).
2. Load it at the prompt cap (`max_model_len` 8192) and record load time (launch to `Application startup complete`) and peak VRAM; a candidate that does not load at the cap is recorded as failed, with the error, and skipped.
3. Run its stage-1 alerts. Stage 2 re-downloads the top 3 the same way.
4. Delete its weights from the HF cache before downloading the next candidate.

## Outputs

`outputs/e18/<stage>/<candidate>/`: a `run_llm_agent.py` run dir (`runlog.parquet`, `per_alert.jsonl`, `traces.jsonl`, `summary.json`, ...) plus `e18_meta.json` (serving stack, quant, repo, revision, server version, argv). Per stage: `summary.csv` / `summary.json` and `size_vs_brier.png` (Brier with CI against active parameters, one line per family; skipped if matplotlib is missing), and `decision.json`.

Columns: Brier with cluster-bootstrap CI (no verdict scored as p0) and the no-verdict rate; valid-output rate (stops + valid DSL over outputs, the rate the rule filters on), valid-DSL rate (valid over composed questions) and JSON parse rate; median and p90 wall seconds per alert; median and p90 GPU seconds (sum of LLM latency); calls, tokens in and out per alert; parameters, active parameters, quant, stack, size in GB (config value or params x bits per weight, labelled). Latency counts only when every run was on the reference machine (`latency_counts` in `summary.json`).

## The decision rule as implemented

Everything uses the paired cluster bootstrap of `ftm.eval.bootstrap.brier_diff` (10,000 resamples, 95%, seed 0 from the config). Clusters come from `--clusters` (alert_id to cluster, from T4's attempt+accounts clustering); without it each alert is its own cluster, which the summary says and which makes CIs too narrow.

1. **Stage 1** (`stage1_select`): drop if valid-output rate < 0.95; drop if the CI of Brier(model) - Brier(best) lies entirely above 0 (lower bound > 0). Best = lowest Brier over all candidates. Keep the top 3 of the survivors by Brier.
2. **Pick** (`pick`): best = lowest Brier of the 3. A model is equivalent if the CI upper bound of Brier(model) - Brier(best) is strictly below the margin. Among equivalent models whose median seconds per alert is within the latency target, take the smallest by active parameters; ties by lower median seconds, then fewer total parameters. If none: the lowest-Brier model that meets the latency target. If no model meets it: no pick.
3. **Thinking arm** (`thinking_decision`): adopt for every system iff the CI upper bound of Brier(on) - Brier(off) < -margin and the on-arm median seconds per alert still meets the latency target. For gpt-oss, "on" means `reasoning_effort: medium` (`gpt_oss_thinking_on_effort`), since it has no thinking switch.

## Questions for Shreyas (T4) where the prereg text is ambiguous

1. **Decided by T3 on 2026-10-26, after stage 1 ran (for T4 to confirm or overrule):** an output is valid if it parsed (JSON + schema) and, when it carried a question, its DSL validated (`ftm.planners.e18.valid_dsl_output_rate`). Selects set aside for lack of eps, duplicates and time refusals are planning errors, not invalid DSL; they stay visible as `usable_output_rate`. **This reading was chosen after seeing that it decides whether Qwen3-14B goes to stage 2** (0.922 under the old reading, 1.000 under this one); gpt-oss-20b (0.874) and Gemma 4 26B-A4B (0.864) fail under either. Was: **Which rate is \"valid-DSL output rate\"?** Implemented: (stops + valid DSL) / outputs, the planner's `usable_output_rate` (a bad JSON output counts as invalid). `valid_dsl_rate` (valid / composed questions) is also reported. A model that always stops would pass either.
2. **Is "best model" in stage 1 restricted to models that pass the DSL filter?** Implemented literally: best over all candidates, so a model with 80% valid DSL and the best Brier can eliminate everything clearly worse than it. Restricting to survivors would be a one-line change.
3. **Latency "8-20 s".** Implemented: median wall seconds per alert <= 20; faster than 8 s is not a failure. Applied as a filter on the equivalent set (the smallest equivalent model that is fast enough), not after choosing the smallest equivalent model.
4. **Margin inputs.** "Brier(random)" is not defined (uniform 0.5? p0 shuffled? the base rate?). The driver takes the two Brier values as input (`--margin-json`); someone has to produce them on the same 460 alerts.
5. **Stage 2 reuse.** "Stage-1 alerts included": implemented as a fresh run of the 3 models on all 460 alerts (stage-1 run dirs are not reused); the first 160 are the stage-1 alerts, checked.
6. **gpt-oss thinking-on** = `reasoning_effort: medium`; is that the arm you want (or `high`)?
7. **Cluster file.** The run log has no attempt ids or accounts. Who writes the alert_id to cluster map for the HI-Medium val alerts, and with which hub cap?
8. **Answered 2026-10-25 (prereg amended):** stage 1 `eval` (160), stage 2 and thinking `all` (460). Was: **Which `--val-part`?** Not specified by plan §9.3 or T4's item 9. `eval` is the selection part per `run_llm_agent.py`, but 500 alerts may exceed the HI-Medium `eval` part (HI-Small `eval` has 332 alerts); T1 reports counts per part.
9. **Exact ties in Brier** are broken by active parameters, then median seconds, then name.

## Not done here

- llama.cpp candidates (Qwen3.8-27B UD-Q3_K_XL, Gemma 4 31B Q3): `scripts/serve_llm.py --model qwen3.8-27b-q3` picks the `llamacpp` backend from `stack: llama.cpp` and runs `llama-server` (path: `FTM_LLAMA_SERVER`, default `~/llama.cpp/build/bin/llama-server`). It resolves `gguf_repo`/`gguf_file` from the sweep config in `FTM_HF_HOME` and never downloads: if the file is missing it prints the exact `hf download <repo> --include <file>` command. Flags: `-m`, `--alias`, `--ctx-size` (= `max_model_len` x slots), `--n-gpu-layers all`, `--parallel 1`, `--seed`, `--jinja`, `--reasoning-format deepseek`, `--chat-template-kwargs {"enable_thinking":false}`, `--no-webui`, `--host/--port` (same `check_host`). The key goes in `LLAMA_API_KEY`, never argv. The `gguf_file` names in the sweep config are guesses at the repo naming: check them against the repo listing when pinning the revision. Gaps vs vLLM: no `--gpu-memory-utilization` or `--generation-config` equivalent; json_schema is enforced by llama.cpp grammar sampling rather than vLLM guided decoding; sampling with a seed is not bit-identical to vLLM. The run log records the stack from the config (`llama.cpp`).
- Revisions, quant repos and `size_gb` for most candidates are `null` in `configs/experiments/e18_backbone_sweep.yaml` until the week-0 model-card checks are done.
