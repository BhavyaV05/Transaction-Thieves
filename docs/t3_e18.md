# E18: backbone size sweep (T3 driver)

Owner: T3 (Akshat). Spec: `plan.md` §6.11 and §8 (E18 row, decision rule), `tracks.md` §5.4 / §5.8. Rule: `prereg/e18_decision.yaml` (T4 owns it; this code only reads it). Config: `configs/experiments/e18_backbone_sweep.yaml`.

Validation only. HI-Medium val alerts (`docs/t4_decisions_week2.md` item 9). `--alerts test` is refused whatever `FTM_FINAL_RUN` says.

## Pieces

| File | What |
|---|---|
| `scripts/run_e18.py` | The driver: `stage1`, `stage2`, `thinking`. Runs each candidate through `scripts/run_llm_agent.py` (same planner loop, compose mode), then tabulates and applies the rule |
| `ftm/planners/e18.py` | Pure code: config, per-candidate metrics from a run dir, the decision rule (stage-1 selection, pick, thinking adoption), parity check, summary table, plot, GPU-hour estimate |
| `tests/test_e18.py` | Rule on synthetic per-alert results; the driver end to end on in-process mock endpoints |

`run_llm_agent.py` gained `--endpoint`, `--model`, `--reasoning-effort`, `--max-output-tokens`, `--max-prompt-tokens`, `--max-llm-calls`, `--serving-stack`, `--candidate`, `--run-id`, `--run-dir`, and writes `per_alert.jsonl` (seconds, tokens, calls, planner counters per alert) next to the run log. Defaults are unchanged for G2/G3 runs.

## Parity (plan §6.11)

Same for every candidate: alerts (a seeded shuffle, so the first 200 are a prefix of the 500), seed 0, `Limits` (`max_tokens` 6,000 is read from `configs/llm/default.yaml` and must equal `parity.max_prompt_tokens`), prompt text (each model's own chat template), temperature 0, top-40 evidence. Thinking off (`enable_thinking: false`); gpt-oss at `reasoning_effort: low`. Before deciding, `check_parity` compares the alert hash, ids, seed, data, val part and limits of every run dir and raises `ParityError` on any difference.

## Commands

The 16 GB GPU holds one candidate at a time: serve a candidate, run it, switch. `--only a,b` runs just those candidates (the decision still waits for the whole stage). The driver skips a candidate whose endpoint does not list its `served_model`, and skips one whose run dir is complete (`summary.json` with the right alert count and settings). An incomplete run dir is deleted and rerun. The decision is applied once every candidate of the stage is complete.

```bash
# plan and GPU-hour estimate (8-20 s per alert; thinking arm 5-9 h per 500 alerts); touches no data, no endpoint
python scripts/run_e18.py stage1 --val-part eval --dry-run --sets core,if_time

# stage 1: ~200 alerts per candidate (FTM_LLM_ENDPOINT / FTM_LLM_API_KEY as usual; --machine t3-5070ti for timing)
python scripts/serve_llm.py --profile qwen3-8b              # one candidate at a time
python scripts/run_e18.py stage1 --val-part eval --only qwen3-8b --machine t3-5070ti --clusters clusters.json
...                                                          # next candidate; the last call writes decision.json

# stage 2: the top 3 from stage 1 (outputs/e18/stage1/decision.json), 500 alerts, stage-1 alerts included
python scripts/run_e18.py stage2 --val-part eval --only gpt-oss-20b --machine t3-5070ti   # --models a,b,c overrides the stage-1 top 3
python scripts/run_e18.py stage2 --val-part eval --only <last model> --machine t3-5070ti --clusters clusters.json --margin-json margin.json

# thinking-on arm for the stage-2 winner: 1,024 output tokens per step, same 500 alerts
python scripts/run_e18.py thinking --val-part eval --machine t3-5070ti --clusters clusters.json --margin-json margin.json

# tabulate and decide from existing run dirs, no model calls
python scripts/run_e18.py stage2 --val-part eval --summarize-only --clusters clusters.json --margin 0.01

# whole driver offline against the mock server (python -m ftm.llm.mock --port 8001 --model qwen3-8b)
python scripts/run_e18.py stage1 --alerts synthetic --n 6 --only qwen3-8b --endpoint http://127.0.0.1:8001/v1 --out outputs/e18_smoke
```

Notes: `--val-part` is required with val alerts and has no default (see Questions). `--toolbox` defaults to `harness` (needs T2's harness v0); `dev` is allowed with synthetic alerts only. `prereg/e18_decision.yaml` must have `status: committed` before a real run (`--allow-draft-prereg` overrides; its status and hash go in every `summary.json`). `margin.json` is `{"brier_random": x, "brier_best_simple": y}` measured on the same 500 alerts; the margin is `0.5 * |difference|` (`ftm.eval.stats.equivalence_margin`).

## Outputs

`outputs/e18/<stage>/<candidate>/`: a `run_llm_agent.py` run dir (`runlog.parquet`, `per_alert.jsonl`, `traces.jsonl`, `summary.json`, ...) plus `e18_meta.json` (serving stack, quant, repo, revision, server version, argv). Per stage: `summary.csv` / `summary.json` and `size_vs_brier.png` (Brier with CI against active parameters, one line per family; skipped if matplotlib is missing), and `decision.json`.

Columns: Brier with cluster-bootstrap CI (no verdict scored as p0) and the no-verdict rate; valid-output rate (stops + valid DSL over outputs, the rate the rule filters on), valid-DSL rate (valid over composed questions) and JSON parse rate; median and p90 wall seconds per alert; median and p90 GPU seconds (sum of LLM latency); calls, tokens in and out per alert; parameters, active parameters, quant, stack, size in GB (config value or params x bits per weight, labelled). Latency counts only when every run was on the reference machine (`latency_counts` in `summary.json`).

## The decision rule as implemented

Everything uses the paired cluster bootstrap of `ftm.eval.bootstrap.brier_diff` (10,000 resamples, 95%, seed 0 from the config). Clusters come from `--clusters` (alert_id to cluster, from T4's attempt+accounts clustering); without it each alert is its own cluster, which the summary says and which makes CIs too narrow.

1. **Stage 1** (`stage1_select`): drop if valid-output rate < 0.95; drop if the CI of Brier(model) - Brier(best) lies entirely above 0 (lower bound > 0). Best = lowest Brier over all candidates. Keep the top 3 of the survivors by Brier.
2. **Pick** (`pick`): best = lowest Brier of the 3. A model is equivalent if the CI upper bound of Brier(model) - Brier(best) is strictly below the margin. Among equivalent models whose median seconds per alert is within the latency target, take the smallest by active parameters; ties by lower median seconds, then fewer total parameters. If none: the lowest-Brier model that meets the latency target. If no model meets it: no pick.
3. **Thinking arm** (`thinking_decision`): adopt for every system iff the CI upper bound of Brier(on) - Brier(off) < -margin and the on-arm median seconds per alert still meets the latency target. For gpt-oss, "on" means `reasoning_effort: medium` (`gpt_oss_thinking_on_effort`), since it has no thinking switch.

## Questions for Shreyas (T4) where the prereg text is ambiguous

1. **Which rate is "valid-DSL output rate"?** Implemented: (stops + valid DSL) / outputs, the planner's `usable_output_rate` (a bad JSON output counts as invalid). `valid_dsl_rate` (valid / composed questions) is also reported. A model that always stops would pass either.
2. **Is "best model" in stage 1 restricted to models that pass the DSL filter?** Implemented literally: best over all candidates, so a model with 80% valid DSL and the best Brier can eliminate everything clearly worse than it. Restricting to survivors would be a one-line change.
3. **Latency "8-20 s".** Implemented: median wall seconds per alert <= 20; faster than 8 s is not a failure. Applied as a filter on the equivalent set (the smallest equivalent model that is fast enough), not after choosing the smallest equivalent model.
4. **Margin inputs.** "Brier(random)" is not defined (uniform 0.5? p0 shuffled? the base rate?). The driver takes the two Brier values as input (`--margin-json`); someone has to produce them on the same 500 alerts.
5. **Stage 2 reuse.** "Stage-1 alerts included": implemented as a fresh run of the 3 models on all 500 alerts (stage-1 run dirs are not reused); the first 200 are the stage-1 alerts, checked.
6. **gpt-oss thinking-on** = `reasoning_effort: medium`; is that the arm you want (or `high`)?
7. **Cluster file.** The run log has no attempt ids or accounts. Who writes the alert_id to cluster map for the HI-Medium val alerts, and with which hub cap?
8. **Which `--val-part`?** Not specified by plan §9.3 or T4's item 9. `eval` is the selection part per `run_llm_agent.py`, but 500 alerts may exceed the HI-Medium `eval` part (HI-Small `eval` has 332 alerts); T1 reports counts per part.
9. **Exact ties in Brier** are broken by active parameters, then median seconds, then name.
