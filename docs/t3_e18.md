## Parity (plan §6.11)

Same for every candidate: alerts (a seeded shuffle, so the 160 stage-1 alerts are a prefix of the 460), seed 0, `Limits` (`max_tokens` 6,000 is read from `configs/llm/default.yaml` and must equal `parity.max_prompt_tokens`), prompt text (each model's own chat template), temperature 0, top-40 evidence. ## Commands

The 16 GB GPU holds one candidate at a time: serve a candidate, run it, switch. `--only a,b` runs just those candidates (the decision still waits for the whole stage). The driver skips a candidate whose endpoint does not list its `served_model`, and skips one whose run dir is complete (`summary.json` with the right alert count and settings). An incomplete run dir is deleted and rerun. The decision is applied once every candidate of the stage is complete.

## Per-candidate procedure

The week-0 check "does each candidate load at the context cap" is not done up front. It is part of the sweep, one candidate at a time, so `/` never holds more than one large model (about 100 GB free):

1. Download the candidate once, at its pinned revision, into `FTM_HF_HOME` (for repos that ship extra weight copies, such as `original/` or `metal/`, exclude them).
2. Load it at the prompt cap (`max_model_len` 8192) and record load time (launch to `Application startup complete`) and peak VRAM; a candidate that does not load at the cap is recorded as failed, with the error, and skipped.
3. Run its stage-1 alerts. Stage 2 re-downloads the top 3 the same way.
4. Delete its weights from the HF cache before downloading the next candidate.

## Outputs

`outputs/e18/<stage>/<candidate>/`: a `run_llm_agent.py` run dir (`runlog.parquet`, `per_alert.jsonl`, `traces.jsonl`, `summary.json`, ...) plus `e18_meta.json` (serving stack, quant, repo, revision, server version, argv). Per stage: `summary.csv` / `summary.json` and `size_vs_brier.png` (Brier with CI against active parameters, one line per family; skipped if matplotlib is missing), and `decision.json`.

Columns: Brier with cluster-bootstrap CI (no verdict scored as p0) and the no-verdict rate; valid-output rate (stops + valid DSL over outputs, the rate the rule filters on), valid-DSL rate (valid over composed questions) and JSON parse rate; median and p90 wall seconds per alert; median and p90 GPU seconds (sum of LLM latency); calls, tokens in and out per alert; parameters, active parameters, quant, stack, size in GB (config value or params x bits per weight, labelled). Latency counts only when every run was on the reference machine (`latency_counts` in `summary.json`).

## The decision rule as implemented

Everything uses the paired cluster bootstrap of `ftm.eval.bootstrap.brier_diff` (10,000 resamples, 95%, seed 0 from the config). Clusters come from `--clusters` (alert_id to cluster, from T4's attempt+accounts clustering); without it each alert is its own cluster, which the summary says and which makes CIs too narrow.

1. **Stage 1** (`stage1_select`): drop if valid-output rate < 0.95; drop if the CI of Brier(model) - Brier(best) lies entirely above 0 (lower bound > 0). Best = lowest Brier over all candidates. Keep the top 3 of the survivors by Brier.
2. **Pick** (`pick`): best = lowest Brier of the 3. A model is equivalent if the CI upper bound of Brier(model) - Brier(best) is strictly below the margin. Among equivalent models whose median seconds per alert is within the latency target, take the smallest by active parameters; ties by lower median seconds, then fewer total parameters. If none: the lowest-Brier model that meets the latency target. If no model meets it: no pick.
3. **Thinking arm** (`thinking_decision`): adopt for every system iff the CI upper bound of Brier(on) - Brier(off) < -margin and the on-arm median seconds per alert still meets the latency target. For gpt-oss, "on" means `reasoning_effort: medium` (`gpt_oss_thinking_on_effort`), since it has no thinking switch.

### Procedure

4. Stop the server. Delete the weights unless this candidate is the current lowest-Brier one; weights that were already in the cache before the script started (the incumbent) are never deleted.
5. The non-LLM EIG reference is computed once on the CPU (`t3_e18_refresh_report.py eig-ref`: frozen `headroom_v1` primary variant, EIG policy over the 440 hypotheses, honest cross-part scoring) on exactly the same 300 alerts.

### Selection rule (FIXED 2 Nov, before any run)

Statistic: Brier of the end-to-end probability (no verdict = p0) over the pooled fit+cal 300 alerts; every difference is a paired cluster bootstrap on attempt+accounts clusters (`outputs/e18/clusters.json`), 10,000 resamples, 95% percentile CI, seed 0 (`ftm.eval.bootstrap.brier_diff`).

1. **Eligible**: valid-DSL output rate >= 0.95 (the prereg stage-1 filter, same definition).
2. **Useful**: eligible and Brier(model) - Brier(EIG reference) has a CI that is not entirely above 0 (beats: upper bound < 0; ties: CI spans 0). A model that is clearly worse than the non-LLM EIG policy is not useful, whatever its rank among LLMs.
3. **Best**: lowest Brier among the useful models.
4. **Equivalent**: useful models whose CI of Brier(model) - Brier(best) has lower bound <= 0 (spans 0).
5. **Pick**: among the equivalent models the one with the fewest active parameters; ties by lower median wall seconds per alert, then fewer total parameters, then name. ("Prefer the smaller/faster model when the CI of the difference spans 0.")
6. If no model is useful: no LLM backbone is picked and the non-LLM EIG policy is the system's answer on this metric. This is a possible and reportable outcome.

**Reported next to the rule, not used to decide it (RIGOR rule, 2 Nov):** for every candidate, the EIG reference and p0, on the same 300 alerts: Brier, log loss, AUC, PR-AUC, ECE, calibration slope, precision / recall / F1 / escalation rate at the threshold 0.3227, share of positives caught in the top 10% by score (the alert table has no day, so a 10% review capacity stands in for per-day capacity), flipped calls (right-to-wrong / wrong-to-right) versus p0 and versus the EIG reference, and per alert the questions, eps spent, LLM calls, tokens in and out, wall and GPU seconds. Each metric difference (model - EIG, model - p0, model - Gemma 4 12B) has a paired cluster-bootstrap 95% CI and a two-sided bootstrap p; Holm is applied across the candidate models within each (comparison, metric) family. The Holm-adjusted p's describe the evidence; the pick still follows rules 1-6.

Not part of the rule and not used to decide: eval-part numbers, latency targets, thinking arms. Latency (median s per alert, GPU s) is reported for every candidate; with `--concurrency 4` the first 8 alerts of each run are timed one at a time (`--timing-sample 8`) for the reference latency.
