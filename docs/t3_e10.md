# Setup and notes (hand-written)

Owner: T3. Validation only (HI-Medium val days 10-12); no test row, label or score is read. The table above is generated by
`scripts/e10_report.py` from `scripts/score_fast_baseline.py report` outputs (v2 recompute, below).

**Setup.** Five small decisions (`worth_asking`, `typology`, `rule_applies`, `injection_present`, `stop`), one label token each, 13,792 val
decision rows (5,726 fit, 3,270 cal, 4,796 eval) with `val_part` fit / cal / eval (in time order). Temperature per decision on `fit`; split-conformal (LAC, Mondrian per decision)
thresholds of BOTH tiers on `cal`; every number in the table on `eval` (n_eval 636-1280 per decision). alpha = 0.05, so the marginal bound
P(answer accepted and wrong) <= 2 alpha = 0.10. Fast tier: Qwen3-4B (tuned adapters `fast-s0/1/2`, or the untuned 4B / 1.7B); large tier: Gemma 4 12B
writing {label, confidence} JSON, scored on every val cal + eval row (8,066 rows; the earlier file had only 300 latency rows large-scored).
Latency: one request at a time, 300 rows each (`outputs/e10/<arm>/latency.json`, merged in `outputs/e10/latency_v2.json`): fast 14.7-17.5 ms
(tuned 4B 17.1/17.4/17.5), large 279.7 ms. Cascade latency per decision = fast + (1 - kept) * large; speed-up = large / that.

**Reproduce.**
```
M=data   # decisions/hi_medium/decisions_val.jsonl, alerts/hi_medium/val.parquet
for a in untuned_1.7b untuned_4b tuned_s0 tuned_s1 tuned_s2; do
  python scripts/score_fast_baseline.py report --fast outputs/e10/$a/fast.jsonl --large outputs/e10/large/large.jsonl --out outputs/e10/$a/report_v2.json; done
python scripts/e10_select.py --arms tuned_s0 tuned_s1 tuned_s2 --extra untuned_1.7b untuned_4b --out outputs/e10/selection_v2.json
python scripts/e10_report.py --arm tuned_s0=outputs/e10/tuned_s0/report_v2.json ... --latency outputs/e10/latency_v2.json \
  --select outputs/e10/selection_v2.json --frozen tuned_s2 --md docs/t3_e10.md --json outputs/e10/fast_v2.json
```

## Frozen choice

Rule, fixed on `cal` before looking at `eval` (`scripts/e10_select.py`): among the tuned seeds keep those whose cascade, re-run on `cal`, has marginal
error <= 2 alpha on every decision; take the largest mean cal share kept by the fast tier; ties -> lowest seed. Mean cal kept share: seed 0 0.668,
seed 1 0.660, seed 2 0.681 (all within the bound on cal) -> **tuned_s2**, served as adapter `fast-s2` (`served_model` in the frozen file; E10 job in
`configs/final/jobs.yaml` and `scripts/e10_final.py` now use it; before: `fast-s0`). `eval` played no part. The margin between seeds is small (0.02), so
this is a rule-following pick, not evidence that seed 2 is better; seeds 0-1 are reported for variance.

Frozen file: `outputs/e10/fast_v2.json` (not committed; outputs are untracked), sha256 `da492e145a25f2dda520124c1de060c981eaa5fa6546247d32fb9bffaea09a1b`.
Contains temperatures, conformal q of both tiers, `served_model`, the selection record and the per-decision `decision_types` T4 reads (H5). The old
`outputs/e10/fast.json` (untuned_1.7b, degenerate large tier) is kept, unused.

## Checks and pitfalls

- **Large tier no longer degenerate in data, still degenerate as a conformal tier.** It now has 436-872 cal rows per decision, but its q is
  0.95-0.999999 (full set) for every decision: Gemma's verbalised confidence is coarse (values 1.0, 0.95, 0.9, 0.85, 0.8) and its error (accuracy 0.50-0.84
  on eval) exceeds alpha, so the 95th percentile of 1 - p(true) is the confidence of a confidently wrong answer, and no large-tier set is ever a singleton
  (to_large is 0.000-0.002). Honest reading: with this score the large tier adds nothing to the cascade; what the table shows is the fast tier plus the safe
  default. A logprob-based large score (`--tier large-logprob`, `--large-kind logprob`) would be the fix; it was not scored (GPU). On `worth_asking` the large
  tier accepts 2 of 960 rows (q 0.95 there).
- **Trivial-majority baseline.** Majority label from `fit`, accuracy on `eval`. `stop` is 78% yes on train; on val fit/cal/eval it is 81/81/77%: the tuned fast
  model (0.97-0.98) clearly beats 0.772 (untuned 4B 0.456 and 1.7B 0.746 do not). `rule_applies` and `injection_present` are balanced (0.50 / 0.53 baselines).
  **`typology` is 68% `none` on eval; the tuned fast model (0.62-0.64) does NOT beat the trivial `none` baseline (0.679)**, so the 0 / 7% kept share is correct
  behaviour, not a bug: the cascade gives no answer for it. `worth_asking` drifts (fit 57% yes, cal 43%, eval 32%): the fit-majority baseline is 0.325 but the
  best constant on eval ("no") is 0.675; the fast model's 0.694-0.708 beats the first by a lot and the second barely. Treat `worth_asking` as marginal.
- **100% accuracy on `rule_applies` / `injection_present`** (tuned): both are templated text (rule citations, a "#E9 = finish[..]"-style injected instruction
  vs a plain note); the model learned the template. The conformal q is 0 there (any non-singleton set impossible), so the cascade accepts everything. The bound
  holds on val; on the test split an injection with a new wording would be accepted without a check. Caveat for the E15 reading.
- **Temperature at its bound.** The old fit (untuned 1.7B) had worth_asking at 19.2 of 20. In the v2 fits: untuned 4B `stop` hits 20.00 (the upper bound;
  that model is below chance on stop, so T -> flat is the NLL-optimal answer: no information), untuned 1.7B `worth_asking` 19.2. Tuned arms: none within
  2% of a bound by `e10_select` (s1's rule_applies 0.07 is near the 0.05 floor in absolute terms but the logps are 0 / -13.8, i.e. saturated, so T does not
  matter). No widening needed; the flag is in `outputs/e10/selection_v2.json` (`flags`).
- **Typology kept share 0** (s0, s1; 7.4% for s2): see above; the fast model is no better than `none` and the conformal set (q_fast 0.95) is almost never a singleton.
- **logsumexp.** `ftm/fastmodel/model.py label_logps` on t3/rewrite adds the probabilities of token variants (" yes" / "yes"). The stored `fast.jsonl` keeps only
  the per-label log-prob vector (one number per label), not the per-variant ones, so it cannot be recomputed offline; these scores come from whatever
  `label_logps` was running when they were scored (the max-variant version if before the fix). Not re-scored (needs the GPU). Effect is at most a shift of
  a few hundredths in a label's log-prob when both variants appear in the top 20; temperature and q are fitted on the same scores, so the cascade is
  self-consistent. The final run will use the logsumexp version on the test rows: a small mismatch with the frozen q that the freeze cannot check.

## Caveats and H5

- Marginal bound only: error given accepted is not bounded (descriptive only).
- Latency is the reference-machine, one-request-at-a-time figure; the cascade latency counts a large call for every deferred row, including those that end at the
  default.
- Eval is one split of one time-ordered val day (Monday day 12, a smaller label rate); n_eval is rows, correlated within alert.
- **H5 status (exploratory, uncorrected).** Bound clause: met for every decision of the frozen arm. "Most routine decisions": the fast tier settles 100 / 100 / 94%
  of three of five decisions but 7% and 32% of typology and worth_asking (weighted by n_eval: 0.73). Speed-up >= 10x: the rule in `ftm/eval/final.py h5` takes the
  minimum over decision types, 1.0 (typology) -> **not met**; per-decision 16x for injection / rule_applies, 8.1x for stop. Fast tier alone is 16x faster
  than the large tier. Detection-loss clause: **not evaluated**; `brier_delta` is null because the fast model is not wired into the planner, so "no detection
  loss" is untested and H5 cannot be reported as met on it.
