# T4 recommendations on the open decisions from T1's weeks 2–4 (PRs #2, #3)

Owner: T4 (Shreyas), as the owner of evaluation and pre-registration. These are **recommendations**, for the team to agree on at the next sync. Each final choice goes into `prereg/` at G3, before any test number exists.

| # | Decision (raised in) | Recommendation | Why |
|---|---|---|---|
| 1 | **The 1,000-alert external subset needs test labels** (`ftm/intake/README.md` item 4) | **Freeze the rule, not the IDs.** At G3, commit the stratification rule, the seed and the code to `prereg/`. At G5, `run_final.py` builds the subset first, writes its ID hash to the run log, and only then runs any system. Stratify on what is known at alert time without labels: home bank × p₀ decile | No test access before G5 and no TA exception needed. External systems only run on test at G5 anyway; on validation they use the val alerts. Label × typology strata are impossible without labels, but bank × p₀ keeps the mix of hard and easy cases |
| 2 | **Alert budget vs launderers missed by intake** (α ≈ 0.6, so about 60% of laundering transactions are auto-cleared; README item 1) | **Keep the budget.** Do not apply the selective-risk bound. Report two levels everywhere: (a) on alerts (gap closed, our headline); (b) **end-to-end over all rows** (alerts + auto-cleared), with the intake miss rate printed next to every result | The agent's compute is finite, and the budget is what the proposal promised (2,500–4,000 test alerts). But a reader must see that intake decides most misses, or gap closed on alerts overstates what the bank recovers |
| 3 | **The plan §5.2 drop rules empty validation** (span rule keeps 42 of 798 val positives; the 72 h window rule removes every val alert) | **Drop the 72 h window rule**; keep the span rule as a flag for a **sensitivity analysis**, not as a filter on the headline set | The window rule only removes alerts whose evidence reaches into an *earlier* split. That is past data, available at `as_of`, so it is not leakage. The span rule protects against memorising attempts whose earlier legs are in train; our defences for that are the shape-filed library, aliases and the shuffled-answers test. Report headline numbers on all alerts, plus the kept-only subset |
| 4 | **HI-Medium test now runs to day 28**: days 17–28 are a sparse tail holding about 31% of test laundering (PR #2) | **Headline test = bulk days 13–16**, as the proposal states. Report the tail separately and never pool it | Only late legs of long attempts live in the tail ("late day means laundering"). Pooling it would reward any model that picks up on time |
| 5 | **Alert definition**: "launder in the prediction set", since no row ever gets both labels (README "Method") | **Accept it.** Rows with an empty set are not alerts, but count them as intake misses in the end-to-end numbers (item 2) | The literal plan rule gives zero alerts. The proposal's intent ("can't confidently rule out laundering") is "launder in set" |
| 6 | **Cluster definition for the bootstrap** (new, from the eval library) | Run `scripts/eval_report.py --on alerts` on HI-Small and HI-Medium val. Use attempt + accounts if `largest_share` < 0.2, otherwise attempt + transaction, and record which | Shared accounts can chain alerts into one giant component, which would make every CI meaningless. The check runs on validation, so the choice is made before test |
| 7 | **"Holm in the order H1 → … → H9"** (plan §2) | **Holm** (step-down by p-value), as the proposal says ("with Holm correction"). The order is for reporting only. `stats.fixed_sequence` exists if the TA prefers that reading | Holm doesn't use a pre-specified order, so the plan's wording mixes two procedures. Either is valid; we just have to name one in `prereg/hypotheses.yaml` |

| 8 | **AML-specific federated method** (T4 week-0 item "confirm with Abhishek"; `docs/t1_week0.md` §3) | **Agree: Tian et al. [8]**, with Ceydeli et al. [9] reimplemented as the fallback | It is the only candidate with code that already reads HI-Small and its Patterns file. It has no licence, so run it from a separate checkout and email the authors this week |

For the team to confirm: items 1–4 change what `tracks.md` and `plan.md` §5.2 say. Once agreed, T4 updates the docs and T1 updates the defaults in `configs/intake/conformal.yaml` and `configs/data/hi_medium.yaml`.
